# Эксплуатация, копии и откат

Команды ниже работают с **явным путём** и не читают `.env`, рабочую базу по умолчанию или файл первоначального пароля. Выполняйте их локально под учётной записью оператора. В лог попадают только количества, технический результат и SHA-256, без имён, телефонов и содержимого пожеланий. Автоматической очистки или отправки сообщений эти утилиты не устанавливают.

Требуется Node.js 22.18+; локальные проверки выполнены на Node 24.22.1. Используется SQLite `VACUUM INTO` через существующие `DatabaseSync`/`prepare`; более новый Node API `sqlite.backup()` не требуется. SQLite описывает `VACUUM INTO` как согласованный снимок работающей БД, включающий зафиксированные данные: [официальная документация](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause). Исходник открывается read-only. Нельзя копировать только основной `.sqlite` обычным файловым копированием во время работы WAL.

## Подготовка и ответственность

Владелец развёртывания назначает оператора, канал реагирования, постоянный диск и каталог копий **вне `public` и `dist`**. Настройте ACL каталога: доступ только оператору и системной службе; на Windows унаследованные ACL проверяются отдельно. POSIX-файл снимка получает режим 0600, но `chmod` не заменяет Windows ACL. Копии содержат контакты и хеши доступа, поэтому храните их на зашифрованном носителе; независимая защищённая копия на другом диске/хосте требует отдельной настройки владельцем.

Предлагаемые цели для небольшого одного экземпляра: ежедневный снимок и снимок перед обновлением (RPO до 24 часов), восстановление до 60 минут (RTO). Это цели для принятия владельцем, а не измеренная гарантия production. Оператор назначает расписание и проверяет последний успешный снимок; отсутствие свежей копии, ненулевой exit или провал контрольного восстановления требуют реакции. Плановый срок копий — 7 дней, если владелец не установил другой срок. Ротация выполняется отдельно после проверки свежей копии; команды ниже старые файлы не удаляют.

Полный комплект восстановления: релизные `server/`, `shared/`, `dist/`, `package.json`/lock-файл, описание версии среды, снимок SQLite и отдельно защищённая конфигурация. Секреты не помещаются в публичный релиз или отчёт. Первоначальный `admin-access.txt` не является резервной копией актуального пароля: после смены он устаревает.

## Проверка и создание снимка

Примеры путей ниже условные. Родительский закрытый каталог должен уже существовать; для каждой копии выбирайте новое имя.

```powershell
node server/ops.mjs verify --database "D:\private\bookings.sqlite"
node server/ops.mjs backup --database "D:\private\bookings.sqlite" --destination "D:\private\backups\pre-update-20261028.sqlite"
node server/ops.mjs verify --database "D:\private\backups\pre-update-20261028.sqlite"
```

Снимок сначала создаётся во временном каталоге рядом с назначением. Утилита проверяет известную схему версии 1, обязательные таблицы/поля, `quick_check`, внешние ключи и записывает файл на диск. Только затем снимок публикуется жёсткой ссылкой с исключительным созданием. Даже пустой существующий файл или ссылка не заменяются. Нужна файловая система с поддержкой hard links (например, NTFS/ext4); если публикация не поддерживается, операция завершается ошибкой, а исходник остаётся нетронутым. Число заявок и SHA-256 возвращаются в JSON; сохраните их в защищённом журнале операции.

Проверяйте ненулевой код завершения. После аварийного выключения незавершённый временный каталог `.ezh-ops-*` не считается копией; перед его отдельной ручной уборкой проверьте точный путь. Утилита очищает только собственные точные временные имена при штатном завершении.

## Восстановление только в новый кандидат

```powershell
node server/ops.mjs restore --database "D:\private\backups\pre-update-20261028.sqlite" --destination "D:\private\candidates\restore-20261028.sqlite"
node server/ops.mjs verify --database "D:\private\candidates\restore-20261028.sqlite"
```

`restore` создаёт новый проверенный файл и удаляет из него **все восстановленные admin-сессии**, сохраняя хеши паролей и историю заявок. Старый файл не заменяется, исходная копия не меняется. Если пароль из снимка неизвестен или мог быть скомпрометирован, после переключения выполните штатный локальный сброс доступа; не публикуйте его результат. Старые cookie после восстановления не должны работать.

До реального переключения проведите пробный запуск на другом loopback-порту с этой БД и **с выключенным Telegram**. Для программного стенда используйте `createApp({ databasePath: candidate, telegram: null, trustedProxies: '', adminCookieSecure: false })`; не запускайте стандартный CLI из каталога с настоящей `.env` для такой пробы. Проверьте вход, сохранённую заявку и историю, статус, новую синтетическую заявку и повтор с тем же ключом. Изолированный кандидат после этой пробы содержит тестовые изменения: для production подготовьте второй новый кандидат из исходной копии.

Перед переключением:

1. Закройте приём новых заявок в выбранном менеджере/прокси и дождитесь текущих операций. Для foreground-запуска используйте штатный Ctrl+C; для службы — настроенную graceful-stop команду её менеджера. Не завершайте все процессы Node на компьютере.
2. Убедитесь, что старый экземпляр остановлен и не держит выбранную БД. Сохраните прежний файл и его WAL/SHM как единый остановленный комплект для возможной сверки; не переименовывайте открытый файл SQLite.
3. В защищённой конфигурации укажите `DATABASE_PATH` нового непубличного кандидата, проверьте `ADMIN_COOKIE_SECURE` для HTTPS, точные доверенные прокси и выбранный релиз приложения.
4. Запустите один экземпляр, проверьте health, вход и основные сценарии. Не включайте внешний приём до успешной проверки.
5. Сверьте заявки после времени снимка: они могут отсутствовать, что составляет фактическую потерю данных в пределах RPO. Старая очередь может повторить ранее принятое Telegram-сообщение; номер заявки помогает сверке. Реальные адресаты и разрешение на внешнюю доставку проверяются отдельно, перед её включением.

## Откат неудачного релиза

Храните предыдущий **цельный** каталог приложения с его `dist` и lock-файлом; одиночного старого HTML недостаточно. Перед обновлением фиксируйте версию приложения, версию схемы, путь конфигурации, время и hash pre-update снимка. Новый релиз сначала проверяется на отдельной синтетической/восстановленной БД. Проверка схемы в этих утилитах принимает версию 1; это не обещание совместимости с произвольным будущим релизом.

При сбое остановите новый экземпляр описанным выше способом. Если схема и данные доказанно совместимы с прошлой версией, можно вернуть прежний цельный каталог приложения с неизменённой БД. Если совместимость не подтверждена, не запускайте старый код на изменённой рабочей БД: восстановите **соответствующий прошлой версии** pre-update снимок в новый кандидат, отзовите его сессии через `restore`, укажите старую конфигурацию с новым `DATABASE_PATH` и запустите прежний каталог. После этого повторите пробу health, входа, чтения/истории, смены статуса, создания и идемпотентного повтора заявки.

Автоматические SQL-миграции при старте и SQL `ROLLBACK` отдельной транзакции не заменяют откат приложения. Для необратимой миграции без совместимого снимка безопасного автоматического возврата нет: приём остаётся закрытым до решения оператора. Прежнюю БД/копию не удаляйте до сверки потерь и принятия результата. Копии и временные стенды затем подчиняются согласованному сроку хранения.

## Срок хранения заявок

Техническое значение по умолчанию — **90 дней от `created_at`**, настраивается явным `--days` (целое 1–3650). Это параметр эксплуатации, не утверждение о законном основании; до сбора настоящих данных оператор согласует срок, политику и требования применимой юрисдикции. Отдельно определяются срок защищённых копий, внешнего Telegram-чата и процедура обращений: локальная очистка не удаляет данные из Telegram, уже выданных копий или сторонних логов.

```powershell
# По умолчанию только подсчёт: база открыта read-only.
node server/ops.mjs purge --database "D:\private\bookings.sqlite"
node server/ops.mjs purge --database "D:\private\bookings.sqlite" --days 90
# Только после проверки подсчёта, pendingNotifications и выбранного пути:
node server/ops.mjs purge --database "D:\private\bookings.sqlite" --days 90 --apply
```

`--apply` удаляет только заявки **строго старше** границы и связанные outbox/history в одной транзакции. Заявка на самой границе остаётся. Сводка включает число ожидающих уведомлений: при истечении срока такие уведомления тоже удаляются, поэтому не применяйте очистку, не оценив результат dry-run. Учётные записи и действующие сессии очисткой заявок не затрагиваются. Ошибка откатывает все зависимые удаления.

Очистка включает SQLite `secure_delete`, но это не гарантия стирания на SSD, в старом WAL, снимках диска или резервных копиях. При необходимости физического уничтожения используйте согласованную процедуру для зашифрованного носителя. Оператор назначает контролируемый ежедневный запуск после проверки на стенде; планировщик и удаление реальных данных этой поставкой не активируются. До настройки расписания одна только команда не означает, что сроки уже исполняются в production.

## Проверка здоровья и журналы

```powershell
node server/ops.mjs health --url "http://127.0.0.1:5173/api/health"
node server/ops.mjs health --url "https://your-domain.example/api/health" --timeout-ms 3000
```

URL задаётся явно, перенаправления и URL со встроенными credentials запрещены. Тайм-аут по умолчанию 3000 мс, разрешён 1–60000 мс; проверяется HTTP-успех, ожидаемый service и `ready:true`. Ошибка, неверная готовность и зависание дают exit 1. Утилита сама никого не уведомляет. Повторный независимый запуск планировщиком и доставка сигнала оператору требуют настройки и проверки в целевом окружении; их нельзя считать проверенными из наличия CLI.

Health не доказывает свежесть копий, доставку Telegram или исправность всего пользовательского сценария. Контролируйте также свежесть/проверку копий, stderr процесса, рост очереди и периодический синтетический сценарий. В access/error-логах прокси исключайте тела формы, cookies/CSRF и query поиска сотрудника (`q` может содержать телефон); проверяйте права и сроки хранения самих логов. Не включайте подробное логирование настоящих запросов ради диагностики.

## CI и границы подтверждения

`.github/workflows/ci.yml` описывает install/build/test/audit для Node 22.18 и 24 на Windows/Linux с read-only repository permissions. `npm test` включает production-сборку и возвращает ошибку при падении теста; `continue-on-error` отсутствует. Для блокировки слияния владелец отдельно выбирает эти проверки как обязательные в настройках GitHub.

Файл workflow не доказывает запуск внешнего CI. Первый реальный прогон матрицы, branch protection, менеджер процессов, TLS, расписание backup/purge, защищённость/независимость копий, RPO/RTO на рабочих объёмах и доставка оповещения остаются проверками после выбора инфраструктуры. При локальном аудите утилиты исполняются только на новых синтетических БД, без внешней доставки и чтения настоящих секретов.
